# Прототипы интерфейса

Здесь лежат макеты, которые согласуются **до** переписывания рабочего кода.
На работу сайта не влияют: каталог закрыт от публикации через `.assetsignore`
и не подключается ни одной страницей.

## `crm-v2.html` — новый интерфейс диспетчерской

Что это: один самодостаточный HTML-файл с демонстрационными данными.
Открывается двойным щелчком в браузере, ничего запускать не нужно.
API не вызывается, данные вымышленные.

### Что изменено по сравнению с текущей CRM

| Сейчас (`crm-next.js`) | В макете |
|---|---|
| Одна колонка: счётчики, поиск, карточки | Три зоны: разделы, список, карточка заявки |
| Карточка заявки — строка в списке, действия внутри неё | Карточка открывается сбоку, действия собраны в одном месте |
| Статус меняется выпадающим списком | Шкала этапов: видно, где заявка и что дальше |
| ~3–4 заявки на экран | ~7–12 заявок: таблица плотнее карточек |
| На телефоне — те же крупные карточки | Плотный список: строка в три строки + быстрые действия (звонок, карточка), на экран помещается вдвое больше заявок |
| Простой заявки не виден | Заявки старше 2 часов помечены ⚠, в сайдбаре сводка |
| На 1180px карточка не помещалась и скрывалась | Карточка выдвигается поверх списка; на телефоне — шторка снизу |

### Цвета

Палитра взята с сайта, чтобы CRM выглядела частью продукта, а не отдельным
сервисом. Ключевые значения:

| Токен | Значение | Где используется |
|---|---|---|
| `--brand` | `#8B2536` | основные действия, активный раздел, номера заявок |
| `--brand-soft` | `#FBF2F4` | подсветка выбранной строки |
| `--st-new` | `#2866A0` | статус «Новая» |
| `--st-processing` | `#B8860B` | «В работе» |
| `--st-transit` | `#19786D` | «В рейсе» |
| `--st-completed` | `#237B50` | «Завершена» |

### Шрифты

Manrope для текста и IBM Plex Mono для чисел, номеров и служебных подписей —
как в текущей CRM. Менять не обязательно, это уже согласовано с сайтом.

## `crm-login.html` — вход в браузерную версию

Что это: макет экрана, который видит диспетчер, когда открывает
диспетчерскую **в обычном браузере** (не в Telegram). Это демонстрация:
реального входа в макете нет, кнопки никуда не ведут, кроме ссылки на бота.

### Зачем браузерная версия

На компьютере WebApp живёт в окне Telegram — тесно, нет вкладок, жестов и
привычного масштаба. Поэтому ПК-версию открывают как обычный сайт, а телефон
остаётся в Telegram: там вход не нужен вообще, личность подписывает сам
Telegram (`initData`).

### Как устроен вход (сценарий)

1. Браузер показывает одноразовый **код** (в макете `482-173`) и кнопку
   «Открыть Telegram» — это deep-link `t.me/asmalinesbot?start=login_<код>`.
2. В чате с ботом пользователь видит, **с какого устройства и города**
   пришёл вход, и подтверждает его кнопкой. Того же можно добиться, просто
   написав в чат `/login 482-173` — например, с телефона, пока ПК-браузер ждёт.
3. Браузер опрашивает сервер, получает подтверждение, ставит сессионную
   cookie и открывает диспетчерскую.

### Меры защиты (для реализации)

- **Одноразовый код**: TTL 5 минут, вход по коду один раз, выдача — не больше
  10 кодов на IP в час.
- **Подтверждение только через бота**: код принимается лишь из чата
  Telegram-аккаунта, который уже есть в списке доступа (`access_users`).
- **Сессия — только cookie**: `HttpOnly; Secure; SameSite=Lax`, срок 30 дней,
  скользящее продление. Хранить в D1 (`sessions`: хеш id, telegram_id,
  создана, истекает, последняя активность, user-agent, признак отзыва).
- **Отзыв**: кнопка «Выйти» в интерфейсе и команда `/logout` в боте
  (отзывает все сессии пользователя).
- **CSRF**: запросы с cookie принимаются только с заголовком
  `X-Requested-With: asma-crm` и совпадающим `Origin`; изменяющие запросы
  без них отклоняются.
- **Один API на два входа**: `/api/crm*` принимает либо подписанный
  `initData` (WebApp), либо сессионную cookie; авторизация — как сейчас,
  по списку доступа.
- **Журнал входов**: кто, когда и откуда вошёл — отдельной таблицей или
  записью в D1, чтобы неожиданный вход был виден.

### Почему не пароль

Пароль нужно заводить, хранить, сбрасывать и защищать от подбора — а
фактический ключ всё равно в Telegram-аккаунте. Подход «код + подтверждение
в боте» даёт вход в один тап, не создаёт новых секретов и отзывается
командой в боте.

## Оптимизация под Telegram (чек-лист для `crm-next.js`)

Раскладка:

- [ ] высота — через `--tg-viewport-stable-height`, не `100vh`: на iOS иначе
      прыгает нижняя навигация;
- [ ] отступы `env(safe-area-inset-*)` в топбаре и нижней навигации;
- [ ] `tg.disableVerticalSwipes()` — чтобы прокрутка списка не закрывала окно;
- [ ] `tg.enableClosingConfirmation()` — если есть несохранённая заметка;
- [ ] тема: `tg.colorScheme` и `tg.themeParams` → тёмная тема,
      `setHeaderColor`/`setBackgroundColor` под фон приложения.

Производительность:

- [ ] удалить мёртвые `assets/crm.js` и `assets/crm.css` (≈18 КБ gzip) — из аудита;
- [ ] не перерисовывать список целиком: точечные обновления строк, debounce поиска;
- [ ] опрос раз в 30 секунд вместо 10, с `ETag`/`If-None-Match`;
- [ ] предзагрузка шрифтов (`<link rel="preload">`) и только нужные начертания.

Под палец:

- [ ] быстрые действия в строке (звонок, открыть карточку) — уже в макете;
- [ ] тач-цели не меньше 44px у главных действий;
- [ ] нативные элементы: `tg.BackButton` для карточки, `tg.MainButton` для
      «+ Заявка» и сохранения заметки.

## Что решено, а что ещё нужно решить

Решено:

1. **Раскладка на 1180px**: карточка заявки больше не скрывается — она
   выдвигается поверх списка (`crm-v2-laptop-detail.png`), на телефоне
   открывается шторкой снизу.
2. **Телефон стал легче**: крупные карточки заменены компактными строками,
   цена, простой и действия — справа; на экран помещается около восьми заявок.
3. **Справочники убраны из макета**: «Автопарк и водители» и «Тарифы и
   маршруты» остаются будущими задачами. «Доступ диспетчеров» в рабочей CRM
   уже есть (`access_users`, `/api/crm/access`) — вернём его отдельным
   разделом, когда дойдём до админки.
4. **Поле «Диспетчер»** — это тот, кто ведёт заявку: принимает её и звонит
   клиенту. В макете выводится `dispatcher`; `assignedTo` (водитель,
   исполнитель) к этому столбцу не относится — он появится в сценарии
   «Подобрать авто».
5. **Браузерный вход**: срок сессии 30 дней и QR-код на экране входа —
   согласованы.

Открытые вопросы:

1. **Статус «Отменена»**: в схеме есть `cancelled`, в текущем интерфейсе он не
   выведен. В макете добавлен — оставляем в работе и фильтрах?
2. **Эмодзи в кнопках**: стоят для наглядности; для продакшна лучше SVG —
   эмодзи по-разному рисуются в Windows, Android и iOS.
3. **Адрес браузерной версии**: оставить общий адрес (сейчас
   `asma-lines-site.firws.workers.dev/crm.html`) или завести отдельный
   поддомен / путь для ПК-версии?

## Как показать макет в Figma

Прямого экспорта в Figma нет, но есть два рабочих пути.

**Вариант 1 — плагин для импорта (быстрее).** Открыть Figma → плагины →
найти `html.to.design` или `Figma to HTML` → вставить в него содержимое
`crm-v2.html`. Плагин разберёт разметку и стили и создаст редактируемые слои.

**Вариант 2 — вставить как изображение.** Перетащить `crm-v2-*.png` на холст
Figma. Подойдёт, если нужен только визуальный ориентир, без редактирования слоёв.
