# План правок ASMA Lines

Разбор проекта по фактам, а не по впечатлениям: каждое утверждение ниже
подкреплено измерением, которое можно перепроверить. Инструменты лежат
в `_tools/`, запускаются одной командой и ничего не меняют.

## Чем измерялось

| Инструмент | Что показывает |
|---|---|
| `node _tools/audit-assets.mjs` | файлы без ссылок, мёртвые CSS-классы, дубликаты |
| `node _tools/audit-css.mjs` | сколько CSS можно выбросить (правила и килобайты) |
| `node _tools/measure-page-weight.mjs` | сколько картинок реально качает браузер на каждой странице |
| `python _tools/measure-image-weight.py` | вес сцены в SVG против WebP в том размере, как она показывается |
| `python _tools/find-static-bands.py` | участки, не реагирующие на смену темы |

## 1. Вес иллюстраций — главная проблема

**Что измерено.** Браузер скачивает на страницах:

| Страница | Картинок | Вес |
|---|---|---|
| `partners.html` | 3 | **444 КБ** |
| `index.html` | 7 | **466 КБ** |
| `services.html` | 6 | **247 КБ** |
| `about.html` | 3 | **234 КБ** |
| остальные | 1–3 | 1–16 КБ |

**Причина** — четыре старых детальных сцены. Они нарисованы контурами
(465–912 путей), но показываются в небольшом окне, где вектор избыточен:

| Сцена | SVG | WebP в размере показа | Экономия |
|---|---|---|---|
| `partners-fleet` | 433 КБ | 23 КБ | 95 % |
| `about-road` | 223 КБ | 27 КБ | 88 % |
| `hero-truck` | 219 КБ | 22 КБ | 90 % |
| `service-auto` | 218 КБ | 10 КБ | 95 % |
| **итого** | **1110 КБ** | **101 КБ** | **91 %** |

**Важно:** новые сцены, которые я нарисовал генератором, переводить не надо —
они весят 7–13 КБ, и WebP для них **хуже** (у CTA-полосы +24 %). Вывод:
переводим только четыре старых тяжёлых сцены, остальное остаётся вектором.

**Что сделать.**
1. Сгенерировать WebP для четырёх сцен: как показывается (`1x`) и вдвое больше
   (`2x`) для экранов с высокой плотностью, отдельно для светлой и тёмной темы.
2. В блоке сцен (`_tools/wire-scenes.mjs`) отдавать эти четыре сцены как WebP,
   остальные — как SVG. Тему выбирать как сейчас, через `[data-theme]`.

**Почему без `image-set()`.** Он подходит для выбора `1x`/`2x`, но широко
доступен только с 18 марта 2026 года: Chrome 113, Firefox 89, Safari 17
([web-features explorer](https://web-platform-dx.github.io/web-features-explorer/features/image-set/)).
То есть Safari на iOS 16 и Chrome до 113 его не поймут. Сам WebP поддержан
намного шире, поэтому основной путь — обычный `url('...webp')`; `image-set()`
можно добавить позже как необязательное улучшение для резкости на retina,
с фолбэком на тот же WebP.

**Ожидаемый результат:** `partners` 444 → ~40 КБ, `index` 466 → ~50 КБ,
`services` 247 → ~45 КБ, `about` 234 → ~40 КБ. То есть страницы станут легче
примерно в десять раз по картинкам.

**Сложность:** средняя — нужен генератор WebP и правка `wire-scenes.mjs`.
**Риск:** низкий: WebP поддержан всеми браузерами, которые сайт обслуживает;
запасной вариант — оставить SVG рядом и не удалять исходники.

## 2. Мёртвый CSS

**Что измерено.** `assets/style.css` — 176 КБ, 7126 строк, 1028 правил.
Из них **189 правил (26 КБ, 1260 строк) не используются**: все их селекторы
ссылаются на классы, которых нет ни в разметке, ни в скриптах. Это ~18 %
файла.

Крупные группы мёртвого CSS:

| Группа | Классов | Что это было |
|---|---|---|
| `network-*` | 11 | старый конструктор маршрутов |
| `route-*` | 9 | поля выбора маршрута |
| `summary-*` | 8 | карточка итога расчёта |
| `src-*` | 7 | карточки результатов поиска |
| `distance-*` | 7 | блок расстояния |
| `panel-*` | 4 | панели конструктора |
| `timeline-*` | 4 | лента этапов |
| `fleet-*` | 3 | теги автопарка |

Всё это заменено компонентом `.express-calc-widget`, который сейчас и стоит
на странице. Мёртвый CSS остался от прежней версии. В `crm-next.css` мёртвое
только одно правило (`sr-only`) — там чисто.

**Что сделать.** Удалить мёртвые правила с проверкой после каждого блока:
снять скриншоты всех страниц в обеих темах до и после, сравнить попиксельно
(`find-static-bands.py` плюс прямое сравнение). Если картинка не изменилась —
удаление безопасно.

**Ожидаемый результат:** `style.css` 176 → ~148 КБ, минус 1260 строк.
Побочная польза: файл станет читаемее, а поиск по нему — осмысленнее.

**Сложность:** низкая. **Риск:** средний — легко задеть живое правило, поэтому
обязательна попиксельная проверка.

## 4. Незавершённое в диспетчерской (Telegram)

Чек-лист лежит в `_prototypes/README.md`. Проверил по коду — сделано уже
больше, чем там отмечено:

**Уже сделано:** стабильная высота (`stable-height`), `safe-area` (9 мест),
`disableVerticalSwipes`, `enableClosingConfirmation`, `setHeaderColor`,
`setBackgroundColor`, `BackButton`. Эмодзи в кнопках заменены на SVG
(0 вхождений) — вопрос можно закрыть.

**Осталось:**

1. **Тёмная тема в Telegram.** `tg.colorScheme` и `tg.themeParams` не
   используются — в интерфейсе всегда светлая. В тёмной теме Telegram
   диспетчерская выглядит чужеродно. *Это самая заметная недоделка.*
2. **`tg.MainButton`** для «+ Заявка» и сохранения заметки — сейчас свои кнопки.
3. **Точечные обновления списка** вместо полной перерисовки + debounce поиска.
   Сейчас опрос раз в 30 секунд перерисовывает список целиком.
4. **Опрос с `ETag`/`If-None-Match`** — сервер умеет отдавать данные, но
   условных запросов нет: каждые 30 секунд прилетает полный JSON.
5. **Тач-цели 44 px** у главных действий на телефоне.

**Сложность:** 1 — низкая; 3 и 4 — средняя (нужна аккуратность, чтобы не
сломать обновление данных); 2 — средняя.

## 5. Согласованность данных

**Нашлось.** В `_shared/core.js` два справочника статусов разошлись:

```js
LEAD_STATUSES      = ['new', 'processing', 'transit', 'completed', 'cancelled']
LEAD_STATUS_NAMES  = { new, processing, calculation, in_transit, transit, completed, cancelled }
```

`calculation` и `in_transit` — мёртвые ключи, а `transit` и `in_transit` дают
одну и ту же подпись «В рейсе / Исполнение». Похоже на переименование,
которое не довели до конца. Опасность: `in_transit` выглядит валидным, но
`isValidStatus('in_transit')` вернёт `false`.

В `schema.sql` колонка `status TEXT NOT NULL DEFAULT 'new'` — без `CHECK`,
то есть база примет любое значение, включая опечатку.

**Что сделать.** Привести справочники к одному набору; добавить `CHECK` на
допустимые статусы в схему (с миграцией) либо оставить свободный текст, но
тогда убрать мёртвые ключи. Добавить тест, что ключи `LEAD_STATUS_NAMES`
совпадают с `LEAD_STATUSES`.

**Сложность:** низкая. **Риск:** низкий.

## Порядок работ

Этапы упорядочены по отношению «польза / риск». Первые три безопасны и
заметны снаружи, дальше — улучшения качества.

| Этап | Что делаем | Пункты | Сложность | Проверка |
|---|---|---|---|---|
| 1 | WebP для четырёх тяжёлых сцен | 1 | средняя | снимки страниц до/после, сверка веса |
| 2 | Чистка мёртвого CSS | 2 | низкая | попиксельное сравнение всех страниц, обе темы |
| 3 | Мусор и дубликаты | 3 | низкая | `npm run check`, проверка 404 в продакшне |
| 4 | Тёмная тема в Telegram | 4.1 | низкая | снимки диспетчерской в `tg.colorScheme` dark |
| 5 | Статусы и схема | 5 | низкая | тест на совпадение справочников |
| 6 | Документация | 6 | низкая | вычитка |
| 7 | Живой список, ETag, тач-цели, MainButton | 4.2–4.5 | средняя | нагрузочная проверка опроса |
| 8 | Мелочи и решение по `server.js` | 7 | низкая | `npm run check` |

Этапы 1–3 дают основной эффект: страницы легче примерно в десять раз по
картинкам, репозиторий легче на 2 МБ, CSS короче на 1260 строк.
